# FRXE Web 0.6.9 Design

## Goal

FRXE Web 0.6.9 will restore reliable web playback on Android, expand Home into a personalized recommendation surface, restructure Search into music-specific result categories, and add both FRXE-generated playlists and manual user playlists.

The web player remains usable without a FRXE account. Listening history, recommendation state, and manual playlists stay local to the browser for this release.

## Scope

0.6.9 includes:

- Repairing the Android/web playback regression introduced by redirecting the browser to extractor-owned direct media URLs.
- Background-capable playback using a real HTML5 audio element and Android Media Session controls.
- A personalized Home feed based on FRXE-local listening signals.
- Search sections for Top Result, Songs, Artists, Genres, and Related Mixes.
- FRXE-generated playlists such as Daily Mix, Discovery Mix, Genre Mixes, Artist Mixes, Throwback Mix, Liked Mix, and Fresh Mix.
- Manual playlists created by the user, with create, rename, delete, add/remove tracks, reorder, Play All, and Shuffle.
- A distinct FRXE Web version set to 0.6.9 that is not overwritten by Android source synchronization.

This release does not add accounts, cloud sync, social playlists, collaborative editing, or a server-side recommendation database.

## Chosen Architecture

### Playback

The current 302 redirect from `/api/audio-stream` to a direct extractor media URL will be removed. Direct media URLs extracted from YouTube or similar providers may be bound to the extractor's IP, cookies, or request headers, so redirecting a different client can fail even when extraction succeeded.

The extractor worker will become the media origin for playback. It will expose a protected playback relay endpoint that:

1. Extracts or resolves the provider audio URL on the worker.
2. Requests the media from the same worker environment that performed extraction.
3. Streams the response back to FRXE Web.
4. Supports byte Range requests so seeking works.
5. Preserves essential media headers such as `Content-Type`, `Content-Length`, `Content-Range`, `Accept-Ranges`, `ETag`, and `Last-Modified` when available.
6. Does not expose the worker token or extractor-owned direct URL to the browser.

The nont.me `/api/audio-stream` endpoint remains the browser-facing route and proxies/relays from the configured extractor worker. The HTML5 `<audio>` player continues to use `/api/audio-stream?id=<videoId>`.

If playback relay fails, the UI must surface the real playback error instead of the obsolete embedded-YouTube error message. FRXE may use the existing iframe path only as an explicit foreground fallback when appropriate; background playback remains the preferred path.

### Player integration

The existing player control contract in `MusicApp.tsx` will be preserved so queue, shuffle, repeat, seek, volume, mute, next/previous, and Media Session behavior do not need separate implementations for each playback backend.

Playback state must continue to drive:

- mini-player state,
- full-player state,
- position and duration,
- auto-next,
- repeat modes,
- Android notification/lock-screen controls,
- Media Session metadata and position state where supported.

## Recommendation System

Recommendations are local and deterministic enough to avoid a completely different Home feed on every refresh.

### Signals

FRXE will derive recommendation seeds from:

- listening history,
- current and recent tracks,
- saved/library tracks,
- artists from saved and played tracks,
- recent search terms,
- genre terms inferred from searches and recommendation rows,
- generated-playlist interactions.

Signals are weighted approximately as:

- 40% played tracks and artists,
- 25% saved tracks and artists,
- 20% genre exploration,
- 15% wildcard discovery.

The exact implementation can vary by available search results, but the output should intentionally mix familiarity and exploration instead of repeatedly returning the same artist.

### Home rows

Home may render rows such as:

- Made for you
- Because you listened to …
- More from …
- Artists you may like
- Explore <genre>
- Fresh mix
- Discovery mix
- Recently played
- Your playlists

Rows should be omitted when they do not have enough useful content rather than rendering empty placeholders.

### Diversity and de-duplication

Recommendation generation must:

- de-duplicate by track ID,
- avoid repeating the same track across adjacent rows where practical,
- limit domination by one artist,
- mix familiar and unfamiliar artists,
- rotate genre seeds,
- cache generated results locally with a timestamp,
- refresh stale recommendations rather than refetching every time Home renders.

A cold-start user with insufficient listening data gets broad discovery using rotating genre and general-music seeds.

## Search Experience

Search keeps the existing `/api/youtube-search` backend but reorganizes presentation and derives additional categories from the returned track metadata.

The result page will contain:

### Top Result

The strongest track or artist-like result for the query.

### Songs

Ranked playable tracks, preserving official/topic/VEVO ranking logic already in shared music search code.

### Artists

Unique artist entities derived from returned tracks. Artist cards are not fake playback tracks. Selecting an artist starts a focused artist search/discovery view.

### Genres

Genre chips/cards based on recognized genre terms in the query and recommendation taxonomy. Genre selection triggers a genre-focused music query and can be used as a recommendation signal.

### Related Mixes

A small set of generated search mixes based on query + artist + genre signals. These are playlist-like collections assembled from fresh search results and can be played/shuffled.

Search must remain useful even when artist or genre classification is weak; Songs is the required baseline result section.

## Playlist Model

### Manual playlists

Manual playlists are immutable from the recommendation engine except when the user explicitly edits them.

A manual playlist contains:

- `id`
- `name`
- `createdAt`
- `updatedAt`
- ordered `tracks`

The user can:

- create a playlist,
- rename it,
- delete it,
- add a search result, recommendation, saved track, or current track,
- remove tracks,
- reorder tracks,
- Play All,
- Shuffle.

Manual playlists persist in localStorage under a versioned FRXE key. Storage parsing must tolerate missing or malformed data and avoid crashing the player.

### FRXE-generated playlists

Generated playlists are clearly labeled as FRXE-generated and are managed by recommendation logic rather than manual editing.

Initial generated playlist types:

- Daily Mix
- Discovery Mix
- Genre Mixes
- Artist Mixes
- Throwback Mix
- Liked Mix
- Fresh Mix

Generated playlists are cached locally and refreshed on a time-based or signal-change basis. Their source rules are stored separately from manual playlist data so generated refreshes can never overwrite user-created playlists.

## Library

Library will separate:

- Saved songs
- Your Playlists
- FRXE Mixes

Existing saved-song behavior remains intact.

## Local Storage

New versioned keys will be introduced for:

- manual playlists,
- generated playlists/recommendation cache,
- recommendation/search preference signals if needed.

Existing history, library, and player settings keys remain supported. New readers must fail safely and fall back to empty/default state when stored JSON is invalid.

## Versioning

FRXE Web will expose a separate constant/version of `0.6.9`.

The automated `scripts/adapt-sources.mjs` source sync may continue to read Android/source metadata, but it must no longer rewrite the FRXE Web release version. Android/source metadata and FRXE Web release metadata are separate concepts.

## Error Handling

Playback errors must identify the actual layer that failed where safe to do so:

- invalid video ID,
- extractor configuration unavailable,
- extraction failed/challenge required,
- upstream media request failed,
- relay/Range request failed,
- browser rejected playback.

User-facing copy should be concise and actionable. The obsolete `This track cannot be played in the embedded YouTube player` message must not be used for background-audio relay failures.

Search and recommendation failures must not break playback or Library. Recommendation rows may fall back to cached data or disappear while core Search remains available.

## Testing Strategy

Implementation follows test-first development.

Required regression/unit coverage includes:

- `/api/audio-stream` no longer redirects the client to the extractor-owned media URL.
- playback relay forwards Range requests and returns partial-content metadata correctly.
- playback errors surface background-audio-specific messages.
- FRXE Web version remains `0.6.9` after source adaptation.
- recommendation scoring mixes history, library, genre, and discovery signals.
- recommendation output de-duplicates tracks and limits artist repetition.
- cold-start recommendation fallback produces useful discovery seeds.
- artist extraction from search results is unique and stable.
- genre classification/search helpers produce expected categories.
- manual playlist create/rename/delete/add/remove/reorder operations preserve track ordering.
- generated playlist refresh cannot mutate manual playlists.
- localStorage parsers survive malformed values.

Browser/E2E coverage should include:

- search shows Songs and artist/genre sections when applicable,
- creating a playlist and adding a song,
- playing a manual playlist,
- Home displays personalized/generated rows after seeded history,
- mini-player/full-player controls still work after the playback transport change.

The existing validation, unit, extractor-worker, build, and Playwright CI pipeline must remain green before the release is considered complete.

## File Boundaries

To avoid further growth of `MusicApp.tsx`, new logic should be split into focused modules where practical:

- `src/music/backgroundAudioPlayer.js` — browser player adapter.
- `src/music/recommendations.js` — seed weighting, de-duplication, mix generation helpers.
- `src/music/playlists.js` — manual/generated playlist data operations and persistence helpers.
- `src/music/searchTaxonomy.js` — artist/genre/result classification helpers.
- `api/audio-stream.js` — browser-facing playback relay/proxy contract.
- `extractor-worker/` — worker-side extraction + media relay implementation.

`MusicApp.tsx` remains the UI composition layer and should consume these modules rather than own all business logic.

## Success Criteria

0.6.9 is successful when:

1. A user can start a playable track in FRXE Web and Android Chrome can continue playback while the app is backgrounded or the screen is locked under normal browser conditions.
2. Playback no longer fails because the browser was redirected to an extractor-bound direct media URL.
3. Search visibly separates Songs, Artists, Genres, and related discovery content.
4. Home provides mixed personalized recommendations rather than only recent tracks.
5. FRXE-generated playlists appear and can be played/shuffled.
6. Users can create and manage their own playlists locally.
7. Manual playlists are never automatically rewritten by FRXE recommendations.
8. The displayed FRXE Web version is 0.6.9 and source sync does not overwrite it.
9. Existing queue, shuffle, repeat, seek, volume, save, Library, Media Session, and responsive behavior continue to work.
